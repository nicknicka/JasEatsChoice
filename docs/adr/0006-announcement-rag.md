# 0006 — 公告 RAG：Qdrant + 按需检索工具

公告包含活动规则、平台说明和商家通知等非结构化文本，现有 Agent 只能依赖结构化工具查询，无法可靠回答“当前有什么活动”“满减规则是什么”等问题。我们决定为公告增加 RAG，但不把订单、优惠券、营养数据等结构化业务数据放入向量库。

## 决策

1. **首期只处理公告。** 教程、菜品描述、商家介绍、节日活动和热门话题后续单独评估。
2. **使用 Qdrant 作为向量库，并优先使用 `langchain4j-qdrant` 官方适配层。** 索引使用单 collection，以 payload `sourceType` 区分内容类型，平台级内容的 `merchantId` 使用 `"platform"`。
3. **检索做成 Agent Tool，而不是全局自动注入。** 公告检索只是 Agent 可调用的知识能力，由 Supervisor 路由后的知识客服 Agent 决定是否调用。
4. **租户和受众过滤必须来自可信运行上下文。** `audience`、`merchantId` 和 `userId` 不能由模型工具参数决定；没有可信上下文时失败关闭。
5. **公告写操作与向量同步解耦。** 公告事务提交后发布领域事件并同步向量；同步失败不回滚公告写，首期提供重建入口，不引入 outbox。
6. **回答必须可追溯。** AI 引用公告标题；涉及活动时说明有效期；没有命中有效公告时明确告知未查询到，不编造规则。

## 考虑过的替代方案

- **自动 RAG 注入**：放弃。当前系统已有结构化工具和 Supervisor 路由，按需 Tool 更符合现有交互，也能避免所有问题都触发向量检索。
- **为公告单独新建完整 Agent**：放弃。检索本身不需要独立推理能力；复用现有客服 Agent 并增加 Tool 即可。
- **首期上 BM25 + 向量混合检索**：暂缓。先用真实问题集验证纯向量效果，出现明确精度瓶颈后再升级。
- **向量同步失败回滚公告写**：放弃。向量是派生数据，Qdrant 或 embedding 服务短暂不可用不应阻止公告发布。

## 后果

- 新增 Qdrant 服务、Embedding 配置和公告重建入口。
- 没有 `ZHIPU_API_KEY` 或 Qdrant 不可用时，应用仍可启动，RAG 能力单独降级。
- 向量模型或维度变化需要新建 collection 并全量重建。
- 后续接入其他内容源时复用同一检索工具、租户过滤和同步链路。
