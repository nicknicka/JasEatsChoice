# 0010 — 提取结果发布为食谱：一对一、营养补 0、来源单独成列

## 背景

「发布为食谱」此前是空实现：只生成一个随机 UUID 当作 recipeId，并把提取结果标记为已发布，`cnt_recipe` 里没有对应记录。用户点完"发布成功"回到「我的食谱」，看不到任何东西。食谱领域模型本身是完整的——实体、服务、接口、表都在，缺的只是这段映射与落库。

同时有两个约束冲突需要定调：提取结果只有一个菜名和一份卡路里，而 `cnt_recipe` 的 `name`、`type`、`calories`、`protein`、`carbs`、`fat` 都是 NOT NULL；产品文档要求"用户可修正提取结果并保存为我的私藏食谱，系统自动标注内容来源以规避版权风险"，但 `cnt_recipe` 没有来源字段。

## 决策

1. **一条提取结果发布为一条食谱。** 映射放在食谱领域内（`RecipeService`），由它负责从提取结果组装食谱；内容提取模块只做归属校验与编排。
2. **`type`（餐次）由用户在发布时选择，默认 `lunch`。** 提取结果里没有餐次信息，不猜。
3. **`protein` / `carbs` / `fat` 缺失时补 0**，不放宽 NOT NULL 约束，用户可在「我的食谱」中后续编辑。
4. **来源单独成列。** 给 `cnt_recipe` 增加来源列，保存原始链接与平台，而不是把来源文字写进食谱正文。
5. **重复发布幂等，并发发布串行化。** 发布事务先对提取记录加行锁；已发布的提取结果再次发布时直接返回既有食谱 ID，并发请求也不会各自创建食谱。

## 替代方案

- **来源写进 `detail`**：不用改 schema，但来源会混进食谱正文、无法查询，后续要拆列时数据已脏。
- **建独立的食谱草稿/审核表**：能承载审核、版本与发布状态机，但当前没有对应需求，属于过度设计。
- **把营养字段改成可空**：要迁移既有约束，并让「我的食谱」各处处理 null，成本高于补 0。
- **在内容提取模块里直接拼 `Recipe`**：少一个接口方法，但食谱字段的默认值逻辑会分散到两个模块，后续必然漂移。

## 后果

- 需要一条 Flyway 迁移，为 `cnt_recipe` 增加来源列。
- 提取结果里的 `dishImage` 与 `difficulty` 在 `cnt_recipe` 中没有对应列，本期不落库。
- 发布后的食谱出现在「我的食谱」列表中，与手工创建的食谱同级。
