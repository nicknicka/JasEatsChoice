# 0003 — 文档清理：只保留当前有效的参考

对 `docs/` 目录进行大规模清理，删除过期的、历史的、与当前实现不匹配的文档，只保留当前仍然有效的核心参考文档。

## 背景

`docs/` 目录有 ~6.9 万行 Markdown，分布在 product、api、testing、delivery、technical、thesis、archive、agents 等多个子目录中。其中包含大量历史文档、毕设论文材料、旧测试报告、已完成的计划文档、过期的技术方案。这些文档不仅没有帮助，反而会误导后续维护者——分不清哪些是当前有效的，哪些已经过时。

## 决策

### 清理原则

1. **10 月份以前的文档默认删除**，除非它描述的是当前仍然有效的核心设计/规范/流程。
2. **计划类文档**：如果计划已完成且没有持续参考价值，删除；如果是当前在用的实施清单，保留。
3. **测试报告**：以 `tests/progress.txt` 为准，旧的测试报告删除。
4. **API 文档**：以运行时 OpenAPI (`/api/v3/api-docs`) 为最终真相，静态 API 文档只保留有业务说明的那份。
5. **毕设论文材料**：全部删除，这是项目仓库不是论文仓库。
6. **archive 目录**：整个删除。归档文档的宿命就是永远不会被再看。

### 保留清单

| 目录 | 保留文件 | 理由 |
|------|----------|------|
| `docs/product/` | `PRD.md` | 当前产品需求，与实现对齐 |
| | `佳食宜选.md` | 产品概述 |
| | `桌面端左侧菜单与页面数据量清单.md` | 当前实现的功能清单参考 |
| `docs/api/` | `后端API文档.md` | 有业务说明的 API 文档（OpenAPI 是真相但缺业务上下文） |
| | `前后端字段对接分析报告.md` | 前后端字段对齐的依据 |
| `docs/testing/` | `test-checklist.md` | 测试检查清单，当前有效 |
| | `implementation-plan.md` | 测试体系的实施方案 |
| `docs/technical/` | `架构清理完成总结.md` | 当前架构状态说明 |

| `docs/adr/` | 全部保留 | 架构决策记录，新增中 |

### 删除清单

- `docs/archive/` — 整个目录（历史归档，不再需要）
- `docs/thesis/` — 整个目录（毕设论文材料，不属于项目仓库）
- `docs/testing/test-report.md` — 旧测试报告，以 progress.txt 为准
- `docs/api/后端API文档_自动生成版_*.md` — 旧自动生成文档，以运行时 OpenAPI 为准
- `docs/api/接口修复计划.md` — 已完成的计划
- `docs/technical/` 中不在保留清单里的其他文件
- `docs/delivery/项目说明.md`、`系统需求分析.md` — 交付期文档，当前以 PRD 为准
- `docs/product/` 中不在保留清单里的其他文件（如果有）

## 考虑过的替代方案

- **保留所有文档，靠目录名区分"当前"和"归档"**：放弃。实践证明归档目录就是坟场，没人会去翻，反而给搜索和浏览增加噪音。不如删干净，需要的话从 git history 找。
- **把过期文档移到 wiki 或别的地方**：放弃。维护成本更高，而且 wiki 也会变成另一个坟场。

## 后果

- 文档量减少约 60-70%，剩下的都是当前有效的
- 后续写文档的门槛提高了——写之前要想清楚"这个文档半年后还有没有参考价值"
- 删除的文档都在 git history 里，真需要可以找回
- `docs/` 目录结构更扁平，找东西更快
