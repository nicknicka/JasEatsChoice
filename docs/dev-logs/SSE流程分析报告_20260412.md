## 四、发现的 Bug 和问题

### Bug 1：SSE 事件重复发送（P0 - 严重）

**现象**：每个子 Agent 的 `AGENT_START` / `AGENT_COMPLETE` 事件被发送 **3 次**，前端收到重复的进度消息。

**日志证据**：
```
00:19:44.728  ⏱️ Agent调用开始: DishRecommendationAgent, 时间=1775924384728
00:19:44.729  ⏱️ Agent调用开始: DishRecommendationAgent, 时间=1775924384729  ← 重复
00:19:44.730  ⏱️ Agent调用开始: DishRecommendationAgent, 时间=1775924384730  ← 重复
```

第三次重复发送时触发错误：
```
❌ [SSE] 发送SSE事件异常: type=AGENT_START, error=ResponseBodyEmitter has already completed
```

**根因**：`SSEAgentListener.inheritedBySubagents()` 返回 `true`，导致同一个 Listener 实例在 Supervisor 层和子 Agent 层都被触发。结合 `SCORED` 响应策略（每个 Agent 被调用2次评分），产生 3 次事件。

**影响**：
- 前端显示重复的进度提示
- SSE 连接因重复发送 `AGENT_START` 导致 `ResponseBodyEmitter has already completed` 异常
- 可能导致部分进度消息丢失

**涉及文件**：`SSEAgentListener.java:315-318`

---

### Bug 2：DishRecommendationAgent 未主动查询用户偏好（P0）

**现象**：第 1 次调用 DishRecommendationAgent 时，它没有查询用户偏好数据，而是反问用户"请告诉我您喜欢的口味"。

**根因**：DishRecommendationAgent 的工具配置中可能缺少用户偏好查询工具，或者 system prompt 中没有引导它先查询偏好再推荐。

**影响**：
- 多了一轮无效的 DishRecommendationAgent 调用（浪费 ~3.4s）
- Supervisor 不得不额外调用 UserPreferenceAgent 再回调 DishRecommendationAgent
- 总共多消耗约 8 秒（无效调用 + 两次规划决策）

---

### Bug 3：推荐数据疑似虚构（P0）

**现象**：推荐结果中的价格和热量看起来不是来自真实数据库：

```
清蒸鲈鱼 - ¥28 - 约100千卡 - ⭐4.7
番茄炒蛋 - ¥15 - 约150千卡 - ⭐4.4
凉拌黄瓜 - ¥8  - 约50千卡  - ⭐4.3
紫菜蛋花汤 - ¥10 - 约60千卡 - ⭐4.2
```

**分析**：日志中未看到任何工具调用（`TOOL_START` / `TOOL_COMPLETE`）记录，说明 DishRecommendationAgent 可能没有调用菜品查询工具，而是 LLM 直接生成了看似合理但无数据支撑的推荐。

**影响**：用户看到的价格、热量、评分均为虚构数据，与实际菜品无关。

---

### Bug 4：Supervisor done 决策耗时过长（P1）

**现象**：从 DishRecommendationAgent 第 2 次完成到 Supervisor 决定结束，耗时 **11796ms**。

**日志证据**：
```
00:20:07.417  DishRecommendationAgent AGENT_COMPLETE
00:20:19.213  SupervisorPlanner → done
00:20:20.200  Response scores: ResponseScore{score1=1.0, score2=1.0}
```

**根因**：`SupervisorResponseStrategy.SCORED` 策略会对每个 Agent 的响应进行评分，需要额外的 LLM 调用来生成评分。`score1=1.0, score2=1.0` 说明两次评分结果完全一致，评分环节价值有限但开销巨大。

**涉及文件**：`SupervisorAgentFactory.java:121`

---

### Bug 5：Supervisor 路由规划错误（P0）

**现象**：用户只发送了一条消息"根据我的口味推荐几道菜"，Supervisor 选择了最差的调用顺序，导致后端 Agent 之间出现了无效的"自问自答"循环。

| 实际调用顺序 | 期望调用顺序 |
|-------------|-------------|
| DishRecommendation → UserPreference → DishRecommendation | UserPreference → DishRecommendation |

**详细分析**：

后端内部发生了以下交互，全程无用户参与：

```
① DishRecommendationAgent（第1次）
   输入: "根据我的口味推荐几道菜"
   输出: "请告诉我您喜欢的口味..."        ← 反问，但没等用户回答

② Supervisor 自动将反问转给 UserPreferenceAgent
   输入: "请告诉我您喜欢的口味..."
   输出: "清淡口味，不吃辣，不油腻"       ← 查了数据库，不是用户说的

③ DishRecommendationAgent（第2次）
   输入: "清淡口味，不吃辣，不油腻"
   输出: 清蒸鲈鱼、番茄炒蛋等推荐
```

**根因**：Supervisor 的 `createSupervisorContext()` 中路由规则是按关键词单匹配的：

```text
菜品/食物推荐 → DishRecommendationAgent
偏好/健康目标 → UserPreferenceAgent
```

缺少组合逻辑——当推荐请求涉及"口味/偏好"时，应先查偏好再推荐。Supervisor 只匹配到"推荐"就直接把原话扔给了 DishRecommendationAgent，导致它因缺少偏好数据而反问，Supervisor 又把反问自动转给 UserPreferenceAgent 查数据库，形成了一个不必要的"自问自答"循环。

**影响**：

- 多了一轮无效的 DishRecommendationAgent 调用（~3.4s）
- 多了两次 Supervisor 规划决策（~7.7s）
- 总共多消耗约 **11 秒**

**涉及文件**：`SupervisorAgentFactory.java:136-158`

## 五、修复建议

### P0 修复（影响功能正确性）

| 问题 | 方案 | 涉及文件 |
|------|------|---------|
| 事件重复发送 | 方案A：`sendEvent` 中基于 `agentId + eventType` 去重<br>方案B：`inheritedBySubagents()` 改为 `false`，只在 Supervisor 层发送 | `SSEAgentListener.java` |
| 未查询用户偏好 | 在 DishRecommendationAgent 的 system prompt 中增加"推荐前必须先调用用户偏好查询工具"的指令 | `DishRecommendationAgent` prompt |
| 虚构推荐数据 | 检查 DishRecommendationAgent 是否正确配置了菜品查询工具，确认工具返回真实数据库数据 | `DishRecommendationAgent` 工具配置 |

### P1 修复（影响性能）

| 问题 | 方案 | 涉及文件 |
|------|------|---------|
| done 决策慢 | 将 `SupervisorResponseStrategy` 从 `SCORED` 改为 `LAST`，避免不必要的评分开销 | `SupervisorAgentFactory.java:121` |
| 路由效率低 | 在 SupervisorContext 中增加路由规则：涉及"口味/偏好"的请求必须先调用 `UserPreferenceAgent` | `SupervisorAgentFactory.java:136-158` |

### P2 优化（锦上添花）

| 问题 | 方案 |
|------|------|
| Supervisor 规划慢 | 使用更轻量的模型（如 Haiku）做路由决策，Sonnet 做子 Agent 实际工作 |
| 日志过多 | `SSEAgentListener.sendEvent()` 中的详细日志降级为 `DEBUG`，减少生产环境日志量 |
