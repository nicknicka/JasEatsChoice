## 缺漏补充（代码核对后）

### 1. 重复保存的根因需明确
- 当前重复写入并非仅“可能重复调用接口”，而是前端存在**两条保存路径**：
    - 路径A：流式最终结果回调中保存一次
    - 路径B：收到`done=true`时再次保存
- 因此同一条AI消息可能被保存两次（与本次ID=1019/1020现象一致）。

### 2. SSE事件语义存在复用
- `COMPLETE`事件同时被用于“初始化提示（正在处理）”和“流程结束（处理完成）”。
- 同一事件类型承载两种语义，前端状态机和日志分析容易产生歧义。

### 3. 性能结论需更细化
- “LLM推理耗时高”成立，但应补充：主要耗时集中在Supervisor阶段的多轮决策与工具编排，不在SSE发送本身。

### 4. 持久化缺少幂等保护
- `/v1/ai/chat/save`当前按请求直接入库，缺少请求级幂等键。
- 在网络抖动、重试、并发点击等场景仍有重复写入风险。
