# 反馈 → PR 两周受控试点

这是一轮**有期限、有上限、可回滚**的试点：验证"用户反馈 → 脱敏 Issue → dsh 开 PR → 按 Delivery requirements 合并"这条链路，
用证据决定要不要扩大范围，而不是先扩大再找证据。

> 试点本身由人执行（跑两周、填台账）；本文件提供范围、门槛、度量口径、停止与回滚条件，以及台账模板。

## 期限与上限

| 项 | 规则 |
| --- | --- |
| 期限 | 2 周 |
| 任务总数 | 最多 3 个 |
| 任务类型 | 只做文档、测试或独立前端任务（低风险） |
| 并发 | 同一时间只运行 1 个（单 worker） |
| 授权 | 准入按 dsh Policy；试点期用 `observe` 档（只记录 Decision），不切 `auto` |
| 合并 | 按 Delivery requirements 执行。试点期未点名 merge CLI，即人工合并；前置就位后再点名 |

## 任务准入

- 只接受**已接受 + 平台系统问题 + 规格完整**的反馈所生成的 Issue。
- Issue 正文必须是脱敏模板（无身份、订单/支付标识、附件正文）。
- 触及支付、订单状态机、权限、部署或生产数据的任务一律**不进试点**。

## 验收门槛（每个任务都必须过）

- `make check`（静态防线）通过。
- 相关 e2e 通过；PR smoke 只跑 `01/04/10`，改动涉及其它 spec 时必须本地补跑对应 spec。
- 合入前人工确认：改动范围与 Issue 一致，无越权文件改动。

## 度量口径

每个任务在台账里记录：

| 字段 | 口径 |
| --- | --- |
| 启动到 PR 耗时 | 授权评论时间 → PR 创建时间 |
| 首轮审查 | 首轮 review 结论（通过 / 返工）与意见条数 |
| 返工轮数 | 首轮之后作者再次提交的次数 |
| CI 结果 | `make check` 与 e2e 的通过/失败 |
| 人工介入次数 | 人工在 dsh 之外介入处理的次数（含等待人工事件） |
| 隐私检查 | 是否触发 `privacy:check` 或人工发现隐私问题 |

## 立即暂停并回滚的条件

出现任一条，立即暂停试点并执行回滚（回滚方式见 `docs/agent-runtime/README.md`）：

- 隐私泄露：真实反馈正文/附件/身份/订单标识出现在 Issue、PR、日志或模型上下文。
- 越权修改：改动超出 Issue 范围或触碰禁用模块（支付/权限/部署/生产数据）。
- 部署或生产访问：代理尝试部署或访问生产服务/数据。
- 连续失败：同一任务连续 2 次失败，或整体出现 2 个失败任务。
- 未遵守 `stop`：人工要求停止后代理仍继续动作。

## 扩大范围的门槛

同时满足才考虑扩大：

- 至少 2 个 PR 经人工审查合并。
- 无隐私泄露、无越权、无生产访问。
- 台账完整，返工与介入次数可解释。

结论必须写明：准入档位（`observe` / `auto`）与合并方式（有无 merge 账号）是否变化，以及依据。
