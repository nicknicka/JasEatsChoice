# 用户反馈接入 dsh-superagent 使用手册

面向五类角色：**用户**、**管理员**、**维护者**、**审查者**、**运维**。每条都写清操作、边界与失败处理。

> 隐私红线：任何时候都不要把真实反馈正文、附件、联系方式、订单/支付标识、日志、密钥或生产界面截图
> 贴进 Git、GitHub Issue、文档或模型上下文。示例与截图只能用合成素材。

## 端到端流程

```text
用户                      管理员                          维护者/研发             dsh 代理
 |                          |                                |                      |
 |-- 提交反馈 ------------->|                                |                      |
 |   (pending 落库)         |-- 分诊: needs_info/accepted/rejected                  |
 |                          |   接受且判定"平台系统问题"        |                      |
 |<-- 回复/内部备注 --------|-- 建 GitHub Issue(脱敏模板) --->|                      |
 |                          |                                |-- 评论 @agent ------>|
 |                          |                                |      (人工授权)       |
 |                          |                                |                      |-- 领任务
 |                          |                                |<---- 开 PR ----------|
 |                          |<---- Issue/PR 关闭回写 ---------|                      |
 |<- 状态/回复 + 通知 ------|                                |-- 人工审查合并 -------|
 |                          |                                |                      |
```

关键规则：

- `ready-for-agent` 只是**队列标签**，加标签不会启动代理；必须维护者评论 `@agent`。
- dsh 只开 PR、不合并、不改标签、不部署；合并与关闭由人完成。
- 通知（站内/WebSocket/邮件）只是提醒，**GitHub Issue 评论才是事实来源**。

## 一、用户：提交反馈、看历史

| 入口 | 路径 | 说明 |
| --- | --- | --- |
| 桌面/Web | `联系客服` 页「提交反馈」 | 选类型 + 填内容（可选联系方式），提交后下方「我的反馈」显示状态 |
| 桌面/Web | `个人资料` / `设置` 里的反馈入口 | 同一接口，归属自动取当前登录用户 |
| 小程序 | `我的 → 意见反馈` | 先建单再上传图片（最多 3 张，单张 ≤ 5MB） |

- 归属由后端从登录态推导，**请求体里的 userId 不生效**。
- 订单/支付类反馈可以关联自己的订单；关联不到也能提交，不阻塞。
- 报错处理：提交失败会提示"反馈提交失败"，重试即可；图片上传失败不影响反馈本身落库。

## 二、管理员：分诊队列、回复、解决

进入后台「反馈管理」，只对拥有 `admin:feedback:*` 权限的账号可见。

| 操作 | 权限 | 说明 |
| --- | --- | --- |
| 列表与筛选 | `admin:feedback:list` | 按状态、类型、用户、商家、订单筛选 |
| 查看详情 | `admin:feedback:detail` | 含全部消息（含内部备注）、附件、关联与审计轨迹 |
| 回复 / 内部备注 | `admin:feedback:reply` | `USER` 用户可见；`INTERNAL` 仅后台可见 |
| 分诊 | `admin:feedback:triage` | `needs_info` / `accepted` / `rejected`；接受时可勾选"平台系统问题" |
| 解决 | `admin:feedback:resolve` | 仅 `accepted → resolved`，必须选结果编码 |
| 修正关联 | `admin:feedback:triage` | 改订单/商家；写入审计，禁止静默改数据 |
| 建 GitHub Issue | `admin:feedback:triage` | 仅"已接受 + 平台系统问题 + 规格完整"；同一反馈只会有一个 Issue |

状态机：`pending → triaging → needs_info → triaging`；`pending/triaging → rejected`；`triaging → accepted → resolved`。
非法流转返回 409。重复/无需修复/无法复现属于**结果编码**，不是状态。

**建 Issue 时必须填全**：脱敏摘要、复现步骤、期望行为、实际行为、验收标准；可加禁止范围与标签。
正文自动带隐藏标记 `<!-- feedback:<id> -->`，用于对账；绝不含身份、订单/支付标识或附件正文。

## 三、维护者：`@agent` 授权

1. Issue 打上 `ready-for-agent`（只是排队）。
2. 授权维护者在该 Issue 评论 `@<agent-login>`，这是**唯一**的人工授权动作。
3. dsh 用专用 GitHub 账号领任务、开 PR，然后停下。

失败处理：若 dsh 等待人工介入、阻塞或失败，平台会产生 `AgentEvent` 并推到站内/WebSocket/（可选）邮件；
到 dsh 面板（`127.0.0.1:8099`）处理后重新授权即可。

## 四、审查者：PR 审查与合并

- dsh 的 PR 与普通 PR 一样走 review；`make check`、相关 e2e、smoke 门槛必须过。
- 人工负责 review、标签、合并、关闭；dsh 不碰这些。
- Issue/PR 关闭后，反馈记录回写为 `resolved` 并给用户一条可见说明。

## 五、通知配置

| 通道 | 编码 | 说明 |
| --- | --- | --- |
| 站内消息 | `in_app` | 系统通知，按接收人用户ID |
| WebSocket | `websocket` | 实时推送 `agent_event` |
| 邮件 | `email` | 默认关闭；正文只有脱敏摘要 + 后台引用链接 |

每个通道可配置：启停、订阅的事件类型、最低严重级别、安静时段（`critical` 穿透）、重试次数。
通道失败只重试该通道并记日志，**不影响 dsh Ticket**。

## 六、模型与运行时配置

后台「Agent 运行时」页面，权限 `admin:agent:runtime`：

- 供应商必须在白名单内（`openai-compatible` / `openai` / `anthropic` / `azure-openai`）。
- 模型、endpoint、数据政策可配置，改动写版本历史。
- 模型 key **只写不可读**：可轮换、测试连接、独立吊销；日志与前端都不回显明文。
- 页面显示 GitHub / DSH profile / 模型 / 隔离账号健康状态。
- `no-merge` / `no-deploy` / `no-production-data` 三条硬边界固定开启，页面无法关闭。

## 七、运维：升级与回退

见 `docs/agent-runtime/README.md` 的「版本锁定与升级 / 回退」。要点：

- 版本锁在 `scripts/agent-runtime/versions.env`；`CHANGE_ME_*` 未填时 `upgrade.sh` 拒绝启动。
- 升级：备份 → 切锁定版本 → 五类探针 → 失败自动回退。
- 回退只恢复升级前备份，**不原地降级**。
- 记录写到仓库外的 `$DSH_LOG_DIR/upgrade-records/`（模板见 `upgrade-record-template.md`）。

## 八、隐私与 Git 禁止跟踪

- 任何 `uploads/` 目录（含 `apps/server/src/main/resources/static/uploads/`）都不入 Git；
  合成素材只放 `apps/server/src/main/resources/static/synthetic-assets/`。
- `make check` 里的 `privacy:check` 会在静态 CI 拦住被跟踪的上传目录与高置信度密钥。
- 凭据只写 `deploy/.env`（已 gitignore）或 CI Secrets；仓库里只留 `.env.example` 占位符。

## 九、失败处理速查

| 现象 | 处理 |
| --- | --- |
| 用户提交失败 | 提示重试；归属与内容校验在后端，错误信息可读 |
| 分诊非法流转 | 409；按状态机重选动作 |
| 建 Issue 报"规格不完整" | 补齐摘要/复现/期望/实际/验收 |
| 建 Issue 报"未配置" | 配置 `GITHUB_BRIDGE_TOKEN` / `GITHUB_BRIDGE_REPO` |
| 通知没到 | 看通道是否启用、订阅与安静时段；邮件默认关闭 |
| dsh 不启动 | 看 `scripts/agent-runtime/dsh-ctl.sh logs`；隔离检查 `verify-isolation.sh` |
| 升级后异常 | 立即 `rollback.sh <备份目录>` 并记录 |

## 十、图文素材要求

- 需要截图时，一律用**合成素材**：合成账号、合成反馈内容、合成订单号，界面不得出现生产域名或真实数据。
- 本手册用流程图 + 标注表格作为等效图文；如后续补截图，放在本目录并以 `synthetic-` 前缀命名。
