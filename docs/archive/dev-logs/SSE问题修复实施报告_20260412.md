## 二、逐任务实施详情

### 任务 1：修复 SSE 重复事件发送

**问题**：每个子 Agent 的 `AGENT_START` / `AGENT_COMPLETE` 事件被发送 3 次，第三次触发 `ResponseBodyEmitter has already completed` 异常。

**改动点**：

1. **`inheritedBySubagents()` 返回 `false`**

   不再将监听器继承到子 Agent，从根源消除 Supervisor 层和子 Agent 层的重复触发。

2. **新增去重保护**

   增加 `Set<String> sentEventKeys` 字段，在 `sendEvent()` 中按 `agentId + eventType` 做幂等判断，已发送过的事件直接跳过。

3. **详细日志降为 DEBUG**

   `sendEvent()` 中的完整数据打印和成功日志从 `INFO` 降为 `DEBUG`，减少生产环境日志噪音。保留错误日志为 `ERROR` 级别。

**涉及文件**：`JasEatsChoiceJava/src/main/java/com/xx/jaseatschoicejava/agent/listener/SSEAgentListener.java`

---

### 任务 2：重写 Supervisor 路由规则

**问题**：路由规则是关键词平铺匹配，无法处理"推荐+偏好"复合意图，导致出现 `DishRecommendationAgent → UserPreferenceAgent → DishRecommendationAgent` 的无效回路。

**改动点**：

将 `createSupervisorContext()` 中的路由规则从：

```text
# 旧规则（平铺）
菜品/食物推荐 → DishRecommendationAgent
偏好/健康目标 → UserPreferenceAgent
```

改为：

```text
# 新规则（优先级 + 组合）

## 复合意图（按顺序调用多个Agent）
1. 推荐+偏好请求 → 先 UserPreferenceAgent，再 DishRecommendationAgent
2. 营养+推荐请求 → 先 NutritionGuideAgent，再 DishRecommendationAgent

## 单一意图（只调用1个Agent）
- 纯推荐（已有偏好）→ DishRecommendationAgent
- 纯偏好设置 → UserPreferenceAgent
...

## 禁止行为
1. 禁止把子Agent的追问当成新任务继续分发
2. 禁止重复调用同一个Agent
3. 单轮请求最多调用3个Agent
```

**预期效果**：输入"根据我的口味推荐几道菜"时，稳定走 `UserPreferenceAgent → DishRecommendationAgent`，不再出现回路。

**涉及文件**：`JasEatsChoiceJava/src/main/java/com/xx/jaseatschoicejava/agent/service/SupervisorAgentFactory.java`

### 任务 3：降低 done 阶段耗时

**问题**：`SupervisorResponseStrategy.SCORED` 在结束前进行额外的 LLM 评分调用，done 阶段耗时近 12 秒，且两次评分结果完全一致（1.0 / 1.0），性价比极低。

**改动点**：

```java
// 旧
.responseStrategy(SupervisorResponseStrategy.SCORED)

// 新
.responseStrategy(SupervisorResponseStrategy.LAST)
```

**预期效果**：done 阶段从 ~12000ms 降至 ~1000ms。

**涉及文件**：`JasEatsChoiceJava/src/main/java/com/xx/jaseatschoicejava/agent/service/SupervisorAgentFactory.java`

---

### 任务 4：收紧 DishRecommendationAgent 输出约束

**问题**：推荐结果中的价格、热量、评分为 LLM 凭空生成，日志中无任何工具调用记录，说明 Agent 跳过了工具直接编造数据。

**改动点**：

将 system prompt 从软约束改为硬约束：

```text
# 旧（软约束）
- 每次推荐都必须调用工具获取真实数据
- 不能凭空编造菜品信息

# 新（硬约束 + 明确后果）
## 强制工具调用规则（违反即为严重错误）
1. 每次推荐前必须先调用至少一个工具，禁止跳过工具直接生成回复
2. 菜品名称、价格、热量、评分只能引用工具返回值，禁止编造
3. 工具返回空结果时如实告知"暂无"，禁止编造菜品填充
4. 偏好信息不足时直接说明，禁止猜测后编造推荐
5. 不允许输出工具结果中不存在的菜名、价格、热量或评分数值
```

**涉及文件**：`JasEatsChoiceJava/src/main/java/com/xx/jaseatschoicejava/agent/agents/DishRecommendationAgent.java`

### 任务 5：核对推荐工具数据链路真实性

**核查结论**：工具链路本身是完整的，所有数据来自数据库查询：

- `queryRecommendations` → `userService.getById()` + `dishService.list()` → 真实数据库
- `getPersonalizedRecommendations` → 同上
- `getHotDishes` → `dishService.list()` 按评分排序 → 真实数据库
- `queryLowCalorieDishes` → `dishService.list()` 按热量过滤 → 真实数据库

**发现的问题**：`queryRecommendations` 虽然获取了用户过敏信息和饮食目标，但没有将饮食目标用于查询条件过滤。

**补充修复**：

```java
// 新增：减肥用户自动过滤高热量菜品
if ("减肥".equals(dietGoal)) {
    queryWrapper.le(Dish::getCalorie, 300);
}
```

同时在 `getPersonalizedRecommendations` 中增加偏好标签日志输出，便于后续排查。

**涉及文件**：`JasEatsChoiceJava/src/main/java/com/xx/jaseatschoicejava/agent/tools/recommendation/RecommendationQueryTools.java`

### 任务 6：补充时间推荐链路与前端展示

**问题**：实际改动中还涉及三餐推荐链路和前端气泡展示，但原报告未纳入，导致“实施范围”和“修改总览”不一致。

**改动点**：

1. **收紧 TimeAwareAgent 的三餐路由提示**

  明确三餐搭配请求优先调用 `recommendDailyMealsByTimeSlots`，避免模型把一日三餐拆成多次单时段调用。

2. **接入真实菜品数据并保留降级兜底**

  `TimeRecommendationTools` 新增真实菜品查询逻辑，优先从 `dish_features` 和 `t_dish` 读取结果；无数据时再回退到静态模板。

3. **修正前端推荐气泡的展示样式**

  `AIChatFull.vue` 中调整了消息气泡与进度提示的布局，避免推荐结果和进度文案在长文本场景下被截断或挤压。

**涉及文件**：

- `JasEatsChoiceJava/src/main/java/com/xx/jaseatschoicejava/agent/agents/TimeAwareAgent.java`

## 五、风险与回退

| 风险 | 影响 | 回退方案 |
|------|------|---------|
| `inheritedBySubagents=false` 导致子 Agent 事件不显示 | 前端看不到子 Agent 进度 | 改回 `true`，仅依赖去重 Set |
| `LAST` 策略在某些场景下结果质量下降 | 最后一个 Agent 的结果不一定是最好的 | 改回 `SCORED` |
| 路由规则仍被 LLM 忽略 | 复合意图仍然路由错误 | 考虑改用代码级路由而非 prompt 路由 |

---

## 六、后续建议

1. **路由规则代码化**：当前路由依赖 LLM 理解 prompt，建议后续用代码做意图分类，只把分类结果传给 Supervisor，减少 LLM 不确定性。
2. **统一推荐 DTO**：工具返回值改为结构化 DTO，减少 LLM 在结果拼装阶段的发挥空间。
3. **补回归测试**：为核心场景（复合意图、单一意图、纯偏好）补充自动化测试。
