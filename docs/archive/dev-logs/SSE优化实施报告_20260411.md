## 一、问题背景

基于 SSE 请求流程分析，典型三餐请求（"帮我安排今天三餐的搭配"）存在以下问题：

| 问题 | 优先级 | 根因 |
|------|--------|------|
| 响应耗时 ~17秒 | P2 | Supervisor 提示词冗长，token 消耗高，决策轮次多 |
| 推荐结果为静态模板 | P2 | `recommendDishesByTimeSlot` 返回硬编码文本，未查询菜品库 |
| TimeAwareAgent 三次独立调用 | P2 | 提示词未强制使用批量工具，LLM 自行拆分为 3 次调用 |

前置已完成项（本次不涉及）：
- P0 前端单路径保存 + 本地去重标记
- P1 clientMessageId 幂等
- P1 SSE 事件类型拆分（INIT / FINISH）
- P2 批量工具 `recommendDailyMealsByTimeSlots` 方法已存在

## 二、修改清单

### 2.1 Supervisor 提示词精简

**文件**: `SupervisorAgentFactory.java` — `createSupervisorContext()` 方法

| 指标 | 修改前 | 修改后 | 变化 |
|------|--------|--------|------|
| 提示词行数 | ~50 行 | ~15 行 | -70% |
| Agent 描述方式 | 每个Agent独立段落（含编号、功能列表、适用场景） | 单行路由规则表 | 大幅缩减 |
| 冗余内容 | 5条核心职责、7条Agent详细说明、3条输出格式要求、2条JSON格式提醒 | 路由规则+3条原则+1条JSON要求 | 去除重复语义 |

**关键改动**：

```text
修改前：
  ## 🎯 核心职责（5条详细说明）
  ## 🤖 L1专家Agent列表（每个Agent 3-4行描述）
  ## 📝 输出格式（3条要求）
  ## ⚠️ 重要提醒（2条）
  ## ⚠️ JSON格式严格要求（3条）

修改后：
  ## 路由规则（7条一行映射）
  ## 原则（4条简洁规则）
  ## JSON格式要求（1条）
```

**新增约束**：
- "单意图只调用1个Agent，不要重复调用"
- "三餐类请求直接路由到TimeAwareAgent，它有批量工具"

**预期效果**：Supervisor 阶段 token 输入减少约 60%，单意图场景决策轮次从 2-3 轮降至 1 轮。

### 2.2 TimeRecommendationTools 接入真实菜品数据库

**文件**: `TimeRecommendationTools.java`

**架构变更**：

```text
修改前：
  recommendDishesByTimeSlot() → buildTimeSlotRecommendation() → switch 硬编码静态文本

修改后：
  recommendDishesByTimeSlot() → buildRealDishRecommendation() → 查询 dish_features + t_dish
                                                ↓ 失败/无数据
                                    buildStaticRecommendation() → 静态模板（降级兜底）
```

**新增依赖注入**：

```java
private final DishService dishService;           // 查询 t_dish 菜品主表
private final DishFeatureMapper dishFeatureMapper; // 查询 dish_features 特征表
```

**查询逻辑**：

1. 通过 `DishFeatureMapper.getByTimePeriod(timePeriodTag)` 查询 `dish_features` 表中 `time_period_tags` 匹配的菜品特征
2. 提取 `dishId` 列表，查询 `t_dish` 表中上架菜品（`is_online = true`）
3. 按 `score` 降序取前 6 条，格式化输出（名称/价格/卡路里/评分/描述）
4. 查询失败或无数据时，降级到原静态模板

**时段映射**：

| 内部时段 | dish_features.time_period_tags |
|---------|-------------------------------|
| 早晨/上午 | 早餐 |
| 中午/下午 | 午餐 |
| 晚上 | 晚餐 |
| 深夜 | 宵夜 |

**输出格式示例（真实数据）**：

```text
🌅 **早晨真实菜品推荐**

1. **番茄鸡蛋面**
   💰 18.00元 | 🔥 380千卡 | ⭐ 4.5分
   📝 经典家常面食，番茄酸甜开胃

2. **豆浆油条套餐**
   💰 12.00元 | 🔥 350千卡 | ⭐ 4.3分
   📝 传统早餐搭配，营养均衡

📊 数据来源：真实菜品库（共匹配6道菜品）
```

**降级策略**：查询异常时自动回退到静态模板，并打印 `WARN` 级别日志，不影响用户体验。

### 2.3 TimeAwareAgent 提示词精简

**文件**: `TimeAwareAgent.java` — `@SystemMessage` 注解

| 指标 | 修改前 | 修改后 |
|------|--------|--------|
| 行数 | ~40 行 | ~15 行 |
| 核心职责 | 4条详细说明 | 移除（工具使用规则已覆盖） |
| 时段划分 | 6条带说明 | 1行简写 |
| 配送时间 | 4条估算值 | 移除（由工具提供） |
| 关键提醒 | 4条 | 2条原则 |

**新增强制约束**：

```text
- 三餐搭配请求 → 调用 recommendDailyMealsByTimeSlots（一次搞定，禁止分3次调用）
```

**预期效果**：三餐场景下工具调用次数从 3 次降至 1 次，对应 LLM 决策轮次从 3 轮降至 1 轮。

## 五、验收步骤

### 5.1 功能验收

1. 启动前后端服务
2. 发送测试消息："帮我安排今天三餐的搭配"
3. 验证返回结果中包含真实菜品数据（名称/价格/卡路里/评分）
4. 若 `dish_features` 表无数据，验证降级到静态模板

### 5.2 性能验收

```sql
-- 验证聊天记录无重复（P0/P1 回归）
SELECT id, user_id, sender, content, create_time
FROM t_ai_chat_history
WHERE user_id = '3384650106421960'
ORDER BY id DESC
LIMIT 6;
-- 预期：每轮对话仅 1 条 user + 1 条 ai
```

观察后端日志中 `⏱️ [耗时]` 输出，预期总耗时 < 8秒。

### 5.3 真实菜品数据验收

```sql
-- 确认 dish_features 表有时段标签数据
SELECT time_period_tags, COUNT(*)
FROM dish_features
GROUP BY time_period_tags;

-- 确认 t_dish 表有上架菜品
SELECT COUNT(*) FROM t_dish WHERE is_online = 1;
```

### 5.4 降级验收

若 `dish_features` 表为空或无匹配数据：
- 后端日志应输出：`📭 [Tool] dish_features 中无时段=xxx 的数据`
- 然后输出：`⏭️ [Tool] 无真实菜品数据，降级到静态模板`
- 前端应正常显示静态模板推荐内容

## 六、风险与回滚

| 风险 | 概率 | 应对 |

| dish_features 表无数据 | 中 | 已内置降级策略，自动回退静态模板 |
