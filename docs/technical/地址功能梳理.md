# 前端地址功能梳理

本文整理了 `JasEatsChoiceFront` 中与“地址”相关的功能，包括用户地址管理、位置选择、地址搜索、商家信息地址展示，以及哪些地方接入了后端、哪些地方使用了本地模拟数据或兜底数据。

## 一、总体结论

1. 用户地址管理已经基本接入后端，包含列表、创建、更新、删除、设默认等操作。
2. 位置选择与地址搜索也主要通过后端代理完成，前端保留了浏览器定位和高德 SDK 作为兜底。
3. 真正使用模拟数据的地方不多，主要是省市区级联数据的本地备用树、定位失败时的默认位置，以及少量静态地区选项。
4. 当前项目里存在两套地址接口风格：
   - 用户地址簿：`/v1/users/{userId}/addresses`
   - 通用地址簿：`/v1/addresses/*`
   两套并存，功能相近，但调用入口不同。

## 二、已接入后端的地址功能

### 1. 用户地址管理页

文件：`JasEatsChoiceFront/src/renderer/src/views/user/Address.vue`

接入方式：
- 获取地址列表：`GET /v1/users/{userId}/addresses`
- 新增地址：`POST /v1/users/{userId}/addresses`
- 更新地址：`PUT /v1/users/{userId}/addresses/{addressId}`
- 删除地址：`DELETE /v1/users/{userId}/addresses/{addressId}`
- 设置默认地址：通过更新接口把 `isDefault` 设为 `1`

数据处理方式：
- 前端把后端字段映射为界面字段：
  - `receiverName` -> `name`
  - `receiverPhone` -> `phone`
  - `detail` -> `street`
  - `isDefault` 的 `0/1` 转成布尔值
- 保存时再把前端表单字段反向映射回后端格式。

特点：
- 这是当前最完整的真实地址簿页面。
- 省市区下拉数据来自后端级联接口，不是固定写死的本地树。

### 2. 通用地址簿封装

文件：`JasEatsChoiceFront/src/renderer/src/api/address.js`

接入方式：
- 列表：`/v1/addresses/user`
- 默认地址：`/v1/addresses/default`
- 新增：`POST /v1/addresses`
- 更新：`PUT /v1/addresses/{addressId}`
- 删除：`DELETE /v1/addresses/{addressId}`
- 设默认：`PUT /v1/addresses/{addressId}/default`

调用位置：
- `JasEatsChoiceFront/src/renderer/src/components/common/AddressSelector.vue`

说明：
- 这套封装更偏通用地址选择器场景。
- 和用户地址管理页使用的 `/v1/users/{id}/addresses` 不是同一套路径。

### 3. 地址级联数据

文件：
- `JasEatsChoiceFront/src/renderer/src/views/user/Profile.vue`
- `JasEatsChoiceFront/src/renderer/src/components/merchant/MerchantInfo.vue`
- `JasEatsChoiceFront/src/renderer/src/composables/useLocation.js`
- `JasEatsChoiceFront/src/renderer/src/views/user/Address.vue`

接入方式：
- 后端级联接口：`GET /v1/location/cascader`

使用场景：
- 个人资料里的“所在地”选择
- 商家信息里的区域地址选择
- 地址管理页里的省市区选择
- 通用位置选择逻辑

### 4. 定位与地址搜索

文件：
- `JasEatsChoiceFront/src/renderer/src/api/location.js`
- `JasEatsChoiceFront/src/renderer/src/components/CommonLocationPicker.vue`
- `JasEatsChoiceFront/src/renderer/src/components/CommonMapLocationPicker.vue`

接入方式：
- 地址搜索：`/v1/location/search`
- 地理编码：`/v1/location/geocode`
- 逆地理编码：`/v1/location/reverse-geocode`
- IP 定位：`/v1/location`
- 行政区数据：`/v1/location/cascader`

特点：
- 高德相关能力现在统一收敛到 Location 入口，前端不再直接依赖旧的 `api/amap.js`。
- 地图选点组件优先调用后端 Location 接口，失败后再退到前端高德 SDK。

### 5. 业务页面中对地址的真实使用

文件：
- `JasEatsChoiceFront/src/renderer/src/views/user/HomeContent.vue`
- `JasEatsChoiceFront/src/renderer/src/views/user/Profile.vue`
- `JasEatsChoiceFront/src/renderer/src/views/merchant/OrderDetail.vue`
- `JasEatsChoiceFront/src/renderer/src/views/merchant/TodayOrders.vue`
- `JasEatsChoiceFront/src/renderer/src/views/merchant/Orders.vue`
- `JasEatsChoiceFront/src/renderer/src/views/user/OrderConfirmation.vue`

说明：
- 首页会把用户选择的位置写回后端用户资料。
- 商家订单页和订单详情页主要展示后端订单中的地址字段。
- 订单确认页当前以“到店自取”为主，显示的是商家地址，不是用户收货地址簿。

## 三、使用模拟数据或兜底数据的地方

### 1. 个人资料页的地址级联备用树

文件：`JasEatsChoiceFront/src/renderer/src/views/user/Profile.vue`

兜底策略：
1. 先请求后端 `/v1/location/cascader`
2. 失败后读取本地缓存 `user_profile_address_options`
3. 再失败则使用内置备用地址树

说明：
- 这是典型的“后端优先，本地缓存其次，静态备用最后”的结构。
- 备用数据主要覆盖北京、上海、广东等常见区域。

### 2. 通用地址选择器的静态区域树

文件：`JasEatsChoiceFront/src/renderer/src/components/common/AddressSelector.vue`

模拟数据：
- `regionOptions` 中写死了北京、上海、广东等少量地区。

说明：
- 这不是后端数据，而是前端内置的地区选择树。
- 适合快速演示和基础选择，但覆盖范围有限。

### 3. 定位失败时的默认位置

文件：
- `JasEatsChoiceFront/src/renderer/src/components/CommonLocationPicker.vue`
- `JasEatsChoiceFront/src/renderer/src/components/CommonMapLocationPicker.vue`

兜底策略：
- 本地缓存优先
- IP 定位其次
- GPS 或高德定位再次
- 最后使用北京默认坐标

说明：
- 这类默认位置不是用户真实地址，只是为了保证页面可用。

### 4. 本地缓存的位置历史

文件：
- `JasEatsChoiceFront/src/renderer/src/components/CommonLocationPicker.vue`
- `JasEatsChoiceFront/src/renderer/src/components/CommonMapLocationPicker.vue`
- `JasEatsChoiceFront/src/renderer/src/views/user/HomeContent.vue`

说明：
- 最近一次位置会被写到 `localStorage`。
- 页面重新打开时会优先恢复上次位置，减少重复定位。

## 四、主要数据流

### 用户地址管理页

用户打开地址管理页 -> 请求后端地址列表 -> 页面映射字段 -> 展示列表 -> 新增/编辑/删除/设默认 -> 再次拉取列表刷新。

### 个人资料所在地

打开个人资料页 -> 请求后端级联地址数据 -> 成功后缓存到本地 -> 页面用级联组件选择所在地 -> 保存时把 location 提交给用户信息更新接口。

### 首页位置选择

首页加载 -> 先尝试恢复本地位置 -> 再走后端 IP 定位或 GPS 定位 -> 选择结果后回写后端用户资料中的 location 字段。

### 商家信息地址搜索

商家信息页加载 -> 请求后端级联地址数据 -> 供区域地址选择使用 -> 通过后端地址搜索接口查找具体位置。

## 五、当前存在的结构性问题

1. 地址接口存在两套并行实现，建议后续统一一套数据契约。
2. 部分页面仍然有静态地区树，维护成本比后端级联数据更高。
3. 地址管理页和通用地址选择器的数据字段命名不一致，容易出现映射重复。
4. 定位组件的兜底逻辑较完整，但也意味着同一份“地址”可能来自后端、缓存、SDK 或默认值，排查问题时需要先确认来源。

## 六、适合继续跟进的方向

1. 统一地址簿接口，明确到底以 `/v1/users/{id}/addresses` 还是 `/v1/addresses/*` 为主。
2. 把静态地区树替换成统一的后端级联数据。
3. 把地址字段映射抽成公共工具，减少页面内重复转换逻辑。
4. 给定位结果和地址来源加统一标识，便于排查“真实地址还是兜底数据”。
