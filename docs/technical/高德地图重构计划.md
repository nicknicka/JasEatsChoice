# 高德地图模块重构计划

## 1. 调研结论

当前项目中的高德地图实现已经收敛到单一业务入口，但底层仍保留高德 SDK / Web 服务两种实现方式作为互补：

- 前端 `CommonMapLocationPicker.vue` 直接加载高德 JS SDK，用于地图渲染、点击选点、Geolocation、CitySearch、Geocoder。
- 前端统一通过 `src/renderer/src/api/location.js` 调用后端定位接口。
- 后端 `LocationController` + `LocationServiceImpl` 负责业务定位入口，底层复用 `AMapService` 请求高德 Web 服务接口，负责搜索、地理编码、逆地理编码、IP 定位。
- 另一个组件 `CommonLocationPicker.vue` 走的是浏览器 `navigator.geolocation` + `/v1/location` 的路线，和地图组件共享同一套定位编排逻辑。

本次问题的根因不是单点错误，而是三层叠加：

1. 高德 IP 接口对当前出口网络返回了成功状态，但没有可用的 province / city / location 数据。
2. 后端原先把这类“空结果”硬判定为失败，返回 500，导致前端进入错误分支。
3. 前端高德 Geolocation 参数曾关闭 `noGeoLocation`，会让插件在某些场景下直接报错，导致备用链路也失败。

## 2. 重构目标

重构的目标不是“把代码改得更长”，而是把职责拆清楚，形成稳定、可维护、可验证的定位链路：

- 前端只负责 UI、交互、地图展示和定位结果消费，不再散落多个重复的定位决策点。
- 后端统一负责高德 Web 服务代理和结果归一化，避免前端直接依赖外部接口细节。
- IP 定位、城市兜底、GPS 定位、默认位置必须形成有序降级链路，且任一环节失败都不应阻断后续环节。
- 同一套定位状态和数据结构在各组件之间复用，避免 `CommonMapLocationPicker` 和 `CommonLocationPicker` 各自实现一套不同的逻辑。

## 4. 新架构设计

### 4.1 前端设计

建议把前端高德相关能力拆成三层：

#### A. SDK 加载层

- 单独抽出一个 `loadAMapSDK` 共享模块，保证只加载一次。
- 使用全局单例 Promise，避免弹窗重复打开时重复插入 script。
- 统一在加载失败时清理状态，允许重试。
- 只在一个位置维护 `securityJsCode` 和 `key`，避免组件内写死配置。

#### B. 定位编排层

- 提取一个共享定位编排器，例如 `resolveLocation()`。
- 统一定义定位顺序：
  1. 本地缓存
  2. 后端 IP 定位
  3. 高德 Geolocation
  4. CitySearch 兜底
  5. 默认位置
- 将“是否已开始定位”的状态集中管理，防止初始化和手动点击同时触发重复链路。
- 明确区分“结果为空”和“请求失败”，空结果继续降级，真正错误才提示异常。

#### C. 业务展示层

- `CommonMapLocationPicker` 只关心地图展示、选点、搜索和确认，不再写一大段定位决策逻辑。
- `CommonLocationPicker` 如果仍然需要城市/经纬度结果，应复用同一套定位编排器，而不是自己再拼一套。

### 4.2 后端设计

建议把 `AMapService` 进一步收敛为“高德适配器”，对外输出稳定 DTO，而不是大量 `Map<String, Object>` 互相嵌套：

#### A. 统一响应模型

- 搜索、地理编码、逆地理编码、IP 定位都返回统一的结构。
- 结构至少包含：`code`、`message`、`data`、`source`、`accuracy`、`hasLocation`。
- 对于 IP 接口的“空结果”，不要再返回 500，而是返回 200 + `hasLocation=false`。

#### B. 统一解析器

- 抽出一个 `AMapResponseParser` 或类似工具类。
- 兼容高德返回的字符串、数组、rectangle、location 等多种字段形态。
- 对 IP 接口优先使用 `location`，没有时使用 `rectangle` 中心点，再没有时返回仅省市信息。

#### C. 统一异常语义

- 高德接口调用失败、JSON 解析失败、鉴权失败，才算真正错误。
- 高德成功返回但字段为空，属于“无可用结果”，应继续降级。
- 日志里要区分：接口失败、解析失败、数据为空、降级成功。

## 5. 具体重写方案

### 5.1 前端重写方案

#### 第一步：抽取共享模块

建议新增以下模块：

- `amap-loader`：负责 SDK 加载、security 配置、重复加载去重。
- `location-resolver`：负责定位链路编排、缓存读写、结果归一化。
- `amap-api`：只保留后端代理请求，不再混合 UI 逻辑。

#### 第二步：重构 `CommonMapLocationPicker.vue`

- 保留地图 UI、搜索 UI、选点确认 UI。
- 去掉组件内部大量重复的定位判断代码。
- 只保留调用 `resolveLocation()` 的入口。
- 统一处理自动定位和手动点击定位结果。
- 删除重复的“开始自动定位”触发点，避免同一次打开弹窗出现两次链路执行。

#### 第三步：重构 `CommonLocationPicker.vue`

- 复用同一个定位编排器。
- 如果它不需要地图展示，就不要再引入高德地图 SDK。
- 只保留城市选择或经纬度回传能力，避免两个组件对外输出不同格式。

#### 第四步：整理配置

- 前端的 AMap Key、securityJsCode 统一改为环境变量驱动。
- 开发环境保留默认值可以接受，但生产环境必须强制使用环境变量。
- 清理不必要的硬编码 fallback，避免误把测试密钥带进生产。

### 5.2 后端重写方案

#### 第一步：规范 IP 定位行为

- 对 `status=1` 但 `province/city/rectangle/location` 为空的返回，视为可降级状态。
- 返回 `200`，并在 `data` 中标记 `hasLocation=false`、`accuracy=none` 或类似字段。
- 不再把“高德返回成功但没结果”映射成 500。

#### 第二步：抽取解析逻辑

- 增加高德响应解析工具，统一处理字符串数组和普通字符串。
- `province` / `city` 需要兼容 `[]`、`["北京市"]`、`"北京市"` 这类返回。
- `rectangle` 需要支持取中心点，作为备用经纬度。

#### 第三步：定义稳定 DTO

- 建议引入专门的响应对象，例如 `AmapLocationResult`、`AmapPoiResult`。
- 避免继续让控制器和前端围绕 `Map<String, Object>` 猜字段。
- DTO 里明确记录 `source`、`accuracy`、`lng`、`lat`、`province`、`city`。

#### 第四步：优化日志

- 日志要能区分以下几类：
  - 高德调用成功但无结果
  - 高德调用失败
  - JSON 解析失败
  - 数据回退到城市级定位
  - 数据回退到默认位置
- 建议把原始响应体只在 debug 级别打印，避免日志过长。

## 6. 分阶段实施计划

### 阶段 1：定边界与协议

目标：先把前后端数据协议和职责边界定下来。

任务：

1. 明确前端只负责展示和调用，后端只负责高德 Web 服务代理。
2. 统一定位结果结构，定义 `hasLocation`、`accuracy`、`source`。
3. 确认生产环境的高德 Key 获取方式，移除硬编码风险。

交付物：

- 一份定位结果数据协议说明
- 一份前后端职责边界说明

### 阶段 2：后端重构

目标：消除 IP 定位硬失败和解析分散问题。

任务：

1. 抽出高德响应解析器。
2. 改造 `ipLocation`，兼容空数组、rectangle、仅省市等场景。
3. 统一 `search/geocode/regeocode/ip` 的成功与失败语义。
4. 为异常、空结果、降级增加清晰日志。

交付物：

- 后端 AMap 代理服务新实现
- 后端单测或手工验证样例

### 阶段 3：前端重构

目标：让前端只保留一个定位编排入口。

任务：

1. 抽取共享 SDK 加载模块。
2. 抽取共享定位编排器。
3. 重构 `CommonMapLocationPicker.vue`，减少重复逻辑。
4. 重构 `CommonLocationPicker.vue`，复用同一结果结构。
5. 修复重复触发自动定位的问题。

交付物：

- 统一定位流程
- 统一返回数据结构
- 减少重复日志和重复请求

### 阶段 4：配置与清理

目标：消除配置耦合和隐患。

任务：

1. 清理前端硬编码 key 或明确仅限开发环境。
2. 校验 Electron CSP 是否允许所有实际用到的高德域名。
3. 统一后端 `application.yml` 的 amap 配置来源。
4. 删除无用的过时注释和重复分支。

交付物：

- 干净的配置入口
- 更清晰的环境变量说明

### 阶段 5：验证与回归

目标：确保重写后链路稳定。

任务：

1. 验证 IP 定位在空结果环境下能自动降级。
2. 验证 Geolocation 不再因为参数配置报错。
3. 验证搜索、逆地理编码、点击选点不受影响。
4. 验证弹窗重复打开不会重复加载 SDK。
5. 验证默认位置和城市级兜底都可工作。

交付物：

- 验证记录
- 回归结果

## 7. 验收标准

满足以下条件即可认为重写完成：

- 打开地图弹窗时，SDK 只加载一次。
- 自动定位链路只执行一次，不出现重复的“开始自动定位”噪音。
- 高德 IP 接口返回空数组时，不再把页面直接打到 500 错误分支。
- Geolocation 的参数不会再主动关闭定位能力。
- 城市级兜底和默认位置能稳定接管失败场景。
- `CommonMapLocationPicker` 和 `CommonLocationPicker` 输出的数据结构一致。

## 8. 风险点

- 高德 IP 定位是否可用，取决于当前出口网络，代码只能保证降级，不可能强行让高德识别出不存在的位置。
- 如果继续保留前端直连 SDK 和后端代理两套路径，后续仍可能产生边界漂移，因此重构时要尽量收敛为一套主路径。
- 生产环境必须确认 AMap Key 和 securityJsCode 的配置来源，否则重构完成后仍可能因环境变量缺失导致初始化失败。

## 9. 建议的最终形态

我建议最终收敛为下面这套模式：

- 前端：地图渲染 + UI 交互 + 调用共享定位编排器
- 后端：高德 Web 服务统一代理 + 响应归一化
- 共享层：统一定位结果模型、统一日志、统一降级顺序

这样做的好处是：

- 定位问题更容易排查
- 不同组件之间不会重复实现逻辑
- 高德返回格式变化时，只需要改一处解析器
- 前端不再被外部接口细节污染
